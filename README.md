# KubeSage

An LLMOps platform for cold-start optimisation and incident diagnosis in Kubernetes.

KubeSage profiles pod startups, detects cold-start problems, diagnoses root causes with an evidence-grounded AI agent, proposes an allow-listed optimisation, tests it in a sandbox namespace and reports measured before/after results.

## Status

Complete end to end: profiler → incident → evidence-grounded AI diagnosis → allow-listed fix proposed by the
Optimization Agent → policy checks → human approval → sandbox before/after experiment → patch for the original
workload, with every decision and cluster change in an audit log. All seven scenarios are detected, diagnosed and
(where an automated fix exists) tested; results below.

Dashboard: http://localhost:5173 (Overview, workload and startup waterfalls, incidents with AI diagnosis and
optimisation, Experiments, Audit, LLMOps).

## Running KubeSage

```powershell
docker compose up -d postgres

# Backend (from backend/)
python -m venv .venv
.\.venv\Scripts\pip install -e ".[dev]"
.\.venv\Scripts\python -m uvicorn kubesage.main:app --port 8000
.\.venv\Scripts\python -m pytest            # unit tests on recorded lab fixtures

# Frontend (from frontend/)
npm install
npm run dev                                 # http://localhost:5173, proxies /api to :8000
```

The backend watches the `demo` and `kubesage-sandbox` namespaces. Each pod start is finalised once Ready:
events and OTel startup spans are joined into a phase timeline, rule-based detectors attribute the time to a
category (large image, slow registry, model loading, app init, capacity, slow readiness), and an incident is
opened when the startup exceeds the workload SLO (default 30 s) or 1.5× its baseline (median of ≥ 3 earlier
startups with the same cold/warm state). Incidents are raised for `demo` only; sandbox startups are profiled
but never raise incidents.

`scripts/capture-fixture.ps1` records a live startup (pod, events, trace) as a test fixture.

## Incident Copilot

"Run diagnosis" on an incident starts a LangGraph agent (Gemini Flash by default; `KUBESAGE_LLM_PROVIDER` /
`KUBESAGE_LLM_MODEL` select another model). It investigates with read-only tools scoped to that incident — pod
events, pod spec, logs, workload history, Prometheus metrics, node capacity, runbooks (`runbooks/`) and past
incidents — all read from data persisted when the pod became Ready, with secrets redacted.

Grounding is enforced in code: every tool result is stored as numbered evidence (E1, E2, ...), every finding must
cite existing evidence, and a diagnosis that contradicts a strong detector result must rule it out. Invalid output
gets one retry with the errors as feedback; if it is still invalid, or the model is unavailable, the run completes
as a clearly labelled detector fallback. Every model call is logged (`/api/llm/calls`) with tokens, latency and
prompt version.

```powershell
# from backend/
python -m evals.run                   # live evaluation against ground truth (evals/scenarios.yaml)
python -m evals.run --mode record     # live, and save validated runs to evals/recordings/
python -m evals.run --mode replay     # replay recordings: no API calls
```

Quota: the Gemini free tier allows 20 requests per model per day and 5 per minute; one diagnosis uses about 4–6.
Per-minute limits are retried after the delay Google suggests; daily exhaustion degrades to the detector
fallback. A paid key is needed for regular use.

## Optimization Agent and controlled testing

"Propose fix" on an incident picks one action from an allow-list (`backend/kubesage/optimizer/catalog.py`) with
bounded, typed parameters; the LLM chooses the action and parameters (validated, deterministic default on failure)
but never writes manifests — patches are generated by code. Actions: `switch_image_variant`, `prepull_daemonset`,
`model_cache_pvc`, `tune_probes`, `adjust_cpu_resources`. Capacity and dependency waits have no safe automated
fix and stay advisory.

Each plan is policy-checked (category fit, parameter bounds, Deployment only, lab mode, one experiment at a time,
no Secrets or foreign PVCs in the clone, sandbox-only writes, and a server-side dry-run as KubeSage's
ServiceAccount), shown as a diff, and waits for a named human approval; approval re-runs the time-sensitive checks
against exactly the reviewed manifests. The experiment then runs in `kubesage-sandbox` on the sandbox node: one
discarded warm-up, alternating baseline/candidate trials, images evicted from the node before every trial (cold
start for both arms), guardrails on every candidate trial (Ready, smoke `GET /predict` via the pod proxy, no
restarts), and cleanup by label. The verdict is *improved* / *regressed* when the median moves by at least
max(2 s, 10 %), *failed* if any candidate trial fails a guardrail. The change for the original workload is exported
as a strategic-merge patch plus objects — never applied automatically.

Measured on the reference machine (medians; trials per arm 3, or 5 for probe and CPU changes):

| Scenario | Action (chosen by the agent) | Baseline | Candidate | Verdict | Note |
|---|---|---|---|---|---|
| S1 large image | switch to `slim` | 43 s | 6 s | improved | cold pull in both arms |
| S2 slow registry | pre-pull DaemonSet | 30 s | 1 s | improved | pre-pull ≈31 s per trial: cost moved, not removed |
| S3 model weights | model cache PVC (1 Gi) | 31 s | 6 s | improved | one-off prefetch 38 s |
| S4 CPU-bound init | CPU 500m request / 1000m limit | 39 s | 14 s | improved | throttling ratio 0.81 before |
| S6a slow readiness | readiness delay 0 s, period 2 s | 65 s | 6 s | improved | readiness detection, not app speed |

## Security model

- The backend impersonates the ServiceAccount `kubesage-system/kubesage` (`deploy/kubesage/rbac.yaml`,
  `KUBESAGE_KUBE_IMPERSONATE`), so the API server enforces least privilege even though the lab kubeconfig is
  cluster-admin: read-only cluster-wide with no access to Secrets, pod logs only in `demo` and the sandbox, writes
  and pod proxy only in `kubesage-sandbox` (with ResourceQuota and LimitRange).
- Lab-mode image eviction (`docker exec … crictl`) is root on the kind node, outside RBAC: it requires
  `KUBESAGE_LAB_MODE=true` and every eviction is audited.
- Secrets in logs and env values are redacted before storage and before any LLM call.
- `/api/audit` lists every proposal, approval, rejection, Kubernetes write, eviction and experiment outcome.

### Scenarios (measured on the reference machine)

| Scenario | What happens | Measured |
|---|---|---|
| `s1-large-image` | 618 MB (compressed) image with unused torch | cold pull 48.8 s (≈34 s transfer + unpack), Ready at 51 s |
| `s2-slow-registry` | small image through the degraded (~2 MB/s) registry path | pull 29.6 s for 53 MB, Ready at 31 s |
| `s3-model-weights` | 250 MB weights downloaded on every start | `model.download` 25–28 s, Ready at 32–34 s |
| `s4-cpu-init` | CPU-bound init under a 250m CPU limit | `init.compute` 34 s, Ready at 42 s |
| `s5-capacity` | 3-CPU request while a hog holds 14 CPUs; hog released after 40 s | Pending 41 s, Ready at 48 s |
| `s6a-slow-readiness` | probes `initialDelaySeconds: 45`, `periodSeconds: 20` | app ready in ~1 s, Ready condition at 61 s |
| `s6b-slow-dependency` | app waits for a dependency that answers after ~40 s | `dependency.connect` 65 s, Ready at 72 s |

`-Cold` stops every demo scenario and removes the demo images from the workload node (`crictl rmi`) so the next start is a true cold pull. This is root access to the node outside Kubernetes RBAC — local lab use only.

### Notes and limitations

- The kind v0.33 node image leaves containerd's registry `config_path` empty; `deploy/kind/cluster.yaml` enables `/etc/containerd/certs.d` explicitly.
- The kubelet `Pulled` duration includes layer unpacking, not just network transfer.
- FastAPI ≥ 0.16x has native OpenTelemetry; the sample app disables it so only startup spans are exported.
- Kubernetes condition timestamps have 1 s resolution.
- The app's process start comes from `/proc` (`btime` has 1 s resolution). When it would place the app start
  before the image pull ended, the profiler clamps it and records `span_clock_skew_s`.
- Pods deleted before becoming Ready (aborted starts) are not recorded; pods that never become Ready
  (e.g. stuck Pending) are not profiled. S5 therefore releases capacity after 40 s, standing in for a node
  being added (kind has no node autoscaler).
- Keep the machine awake during experiments: Windows Modern Standby pauses the cluster; a trial caught in it
  times out and is reported as failed (excluded from the medians).
- Small samples (3–5 trials per arm): results are demonstrations, not statistical significance. Candidate trials
  of `model_cache_pvc` may benefit from the page cache.
- `model_cache_pvc` and the smoke check rely on the demo app's contract (`MODEL_URL`/`MODEL_DIR`/`MODEL_CACHE`
  env, `GET /predict`).
